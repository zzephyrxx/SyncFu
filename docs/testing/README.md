# SyncFu 0.1.0 双机测试

使用同一份 0.1.0 源码分别构建 Windows 和 macOS，两端均打开 **SyncFu**。应用标识统一为 `org.syncfu.desktop`，协议为 **5**、状态 schema 为 **3**；两端均须升级，不可与协议 4 或更早客户端混用。构建方法见 [构建指南](../building.md)。

本指南定义测试过程和预期，不表示实体双机测试已经通过。普通 SyncFu 配对、任务和设置可能保留；此次测试仅新增专用测试目录和任务，不清空已有应用数据。

## 准备

1. 两台电脑接入可互通的 IPv4 局域网，退出旧 SyncFu 进程。仅关闭窗口可能仍留在托盘／菜单栏；两端默认使用 TCP `47657`。
2. 确认两端是同一份源码包或同一 Git 提交。源码包可在各自平台运行 `node scripts/build.mjs windows --verify-only` 或 `node scripts/build.mjs macos --verify-only` 核对。
3. 在源码根目录创建新的测试资料目录，命令拒绝覆盖已存在的目录：

```bash
# 在 Mac 执行
node scripts/test-data.mjs init --side mac --root test-data/mac

# 在 Windows 执行
node scripts/test-data.mjs init --side windows --root test-data/windows
```

两端初始报告均应为 `pass: true`。测试工具只操作显式指定的测试根目录；不将整个源码、桌面、文档或日常资料目录授权给测试任务。

## 连接与授权

1. Windows 进入「设备 → 连接设备 → 等待连接」。Mac 发起连接，选择扫描到的 Windows，并输入它显示的五位配对码。自动发现不可用时才使用 IP 备用入口。
2. Windows 确认请求，等到两端均显示连接就绪。
3. 两端分别授权各自测试根目录中的 `01-bidirectional`，建立“这是我自己的设备／双向”任务，并在对端确认首次关系。
4. 核对两端设备、目录、规则一致且没有待确认的策略，再开始文件操作。

## 大目录扫描与规则确认回归

- 更新两端到本次 0.1.0 构建并退出旧托盘进程，再对同一任务点击「检查变化」。扫描面板应分别显示本机／对端的阶段、当前相对路径、发现的文件和目录数、已校验文件数、当前批次待校验数、已读取字节及用时。发现和校验会交替进行；目录发现结束前总量未知，不显示虚构百分比，也不能因一批文件校验完就提前显示整次扫描完成。
- `Too many open files (os error 24)` 表示同时打开的句柄耗尽，不代表文件总数超限。本次修复移除待扫描任务保留的目录句柄；每个进程同时进行一轮扫描，最多 4 个文件读取线程。大文件每约 150ms 报告实际已读字节，界面按快照刷新。
- **不再限制单任务 20,000 条目**。每收集 256 个文件就先校验这一批，再继续发现文件；大量目录不需要手动拆任务。工作队列与读取缓冲有界，但完整 manifest、比较计划和逐文件状态仍为 O(n)，不可把这个改动理解为任意规模下固定内存。
- 对等消息以最多 256 KiB 的帧分批传输，较大的序列化 JSON 暂存到自动清理的临时文件，移除原 32 MiB 单消息限制。配对前消息仍累计限制为 32 KiB；截断、错序、缺少结束帧和超限小消息必须报错，不得当作成功接收。已配对连接等待请求首字节最多 30 分钟，消息开始后的每帧 IO 有 90 秒停滞期限；长扫描与工作 RPC 的业务等待期限为 30 分钟。
- 扫描发生错误时，已经发现的变化仍可查看，但不能作为完整清单执行同步。错误过多有独立提示；权限、符号链接或路径问题应修复后重新检查。
- 「接受」应有清晰底色和可读文字；收到待确认规则时不显示旧「核对策略」。本机已经答复、仍等待另一端时，「刷新确认状态」保留弹窗并说明正在等哪台设备；它也用于恢复断线后已持久化的确认。
- 设备条目直接提供「解除配对」。确认弹窗应展示设备和受影响任务；取消不改变连接。确认后仅移除本机配对、目录授权和关联任务，不删除实际文件。

自动回归覆盖低文件描述符上限下的宽／深目录、超过原条目限制的扫描、扫描期间目录被替换为符号链接、单文件到 EOF 前的字节进度、真实本地 TLS 双节点进度、授权隔离与不完整扫描阻止写入，以及大消息分帧、截断、配对前累计限制。具体测试结果以该提交的检查记录为准，不能替代 Windows 原生和实体双机验收。

## 大任务同步与逐文件反馈

1. 在专用测试目录准备超过 20,000 个普通文件，包含多个子目录、中文路径和一个足够观察字节进度的大文件；仍只建立一个同步任务。
2. 观察两端扫描阶段和计数持续变化。完整扫描后应出现全部可执行变化，且没有要求拆任务的条目上限错误；如有真实扫描错误，应说明原因并保持同步禁用。
3. 同步所选文件，检查总项目进度、总传输字节、当前文件及其进度。文件完成传输后可显示「已传输」，只有实际应用确认后才能打勾、计入「已同步」；等待和已完成项目应能分别查看。
4. 在接收端落盘阶段继续观察文件完成数，不能只在整个任务结束后一次性跳到完成。长任务仍应显示正在备份、传输、校验、应用或核对的阶段。
5. 专门执行一次中断测试：保留已完成文件的标记，对未确认项目保持待处理／未完成，核对历史与两端文件内容；不得把已传输字节等同于全部文件同步成功。
6. 在总览切换近 7／30 天与「图表／热力图」，只有已完成的真实同步计入统计。热力图强度对应每日文件数，悬停或键盘聚焦后应显示完整日期、文件数、传输量和同步次数，提示不能被图表边缘裁掉。

## 内容校验

每项操作后在两端分别执行，替换根目录和阶段：

```bash
node scripts/test-data.mjs check --root test-data/mac --stage bidirectional-unresolved
node scripts/test-data.mjs check --root test-data/windows --stage bidirectional-unresolved
```

| 阶段 | 检查内容 |
| --- | --- |
| `initial` | 四个目录的初始资料 |
| `bidirectional-unresolved` | 普通项同步、冲突各自保留 |
| `bidirectional-resolved-mac` | 冲突采用 Mac 原版 |
| `one-way-updated` | 接收端独有文件仍保留 |
| `mirror-cleared` | 镜像清理完成 |
| `mirror-restored` | 撤销后原字节恢复 |
| `shared-synced` | 共享文件到达接收端 |

保留中间状态可将 `check` 换为 `snapshot`，不传 `--stage`。报告写入测试根下的 `reports/`，只含相对路径、大小、指纹和差异，不包含文件正文或凭据。工具忽略 `.syncfu-stage` 和系统元文件；不要手动清理应用内部暂存目录。
