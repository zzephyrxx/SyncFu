## 一、访谈确定的范围
| 维度 | 已确认要求 |
|---|---|
| 用户任务 | 个人双机交替工作、主机向副机分发/留副本、多设备/多人使用、非技术用户上手 |
| 平台与网络 | 沿用 macOS / Windows 桌面应用；仅同一局域网、无账号、无外部服务 |
| 规模与拓扑 | 典型目录一万文件以内；多设备通过多条一对一任务组织，不建设共享集群 |
| 方向 | 每个任务独立选择双向、单向更新或单向镜像，不与配对发起/接受角色绑定 |
| 触发 | 手动与全自动同等重要；连接后可开启“有改动自动同步”，已配置自动任务重连后恢复运行 |
| 冲突 | 查看两端差异；指定一端覆盖；暂不处理；批量操作与规则 |
| 不处理 | 分清“稍后处理”“忽略当前版本”“永久排除路径” |
| 信任与权限 | 个人设备互管；他人共享由任务所有者管理策略，不扩大接收端本机授权 |
| 删除安全 | 可自动传播删除，异常时熔断，覆盖/删除前备份 |
| 视觉 | 安静的原生工具：任务侧栏 + 详情，克制用色、清楚按钮层级，不做花哨仪表盘 |
| 便携 | 轻量且尽量免安装、零账号零外部服务、配置可导出迁移；非移动盘携带身份模式 |
| 创意 | “离开前一键交接”；未选择的拖拽连线、同步收据卡片、复杂定时规则不列必做 |
| 顺序 | 先交互原型，再完整可运行闭环；不先做孤立的皮肤替换 |

**非目标：** 公网穿透/中继、云账户、多人多端版本集群、NAS/移动盘专项支持、活动数据库一致性、系统元数据保真、十万文件专项、AI 自动判断文件取舍、文本自动合并。保留双方冲突副本未被选择，不作为必做。文件/目录结构冲突与非法跨平台文件名必须有明确阻塞原因和人工修复路径，不能伪装成普通文件覆盖。

## 二、已核实的工程基础与复用点
- `package.json`：React 19、TypeScript、Vite、Radix、Lucide；Tauri 2 桌面壳。沿用组件库与技术栈。
- `src/App.tsx`：任务/设备/历史/设置组合与 inspect/execute 流程；`src/WindowToolbar.tsx`：导航/任务切换；`src/styles.css`：主题变量、原生字体、响应式、减少动画与透明效果支持。
- `core/src/model.rs::compare`：Manifest/SHA-256 + Baseline 的双向差异比较；`Task` 尚无方向、信任、自动策略。
- `core/src/node.rs::create_task`：两端建立镜像任务；`mirror` 翻转 target；配对角色不是同步权限。
- `src/DiffView.tsx::defaultSelection` 默认选新增/更新，冲突禁选；`Node::execute` 接收 selected 路径并拒绝冲突。因此新增覆盖决策必须改动契约与后端，不能只启用复选框。
- `Engine::begin/backup/seal/apply/finish`：路径与内容校验、备份、依赖检查、批次执行、历史/基线更新；`Node::inspect_undo/reconcile`：撤销和部分完成核对。必须复用这些保护。
- `Node::watch` 已监听变化；`Node::start` 约 7 秒查询对端 dirty，当前不自动执行；已有设备级 coordinator 和单活动批次约束，可复用串行调度。
- `core/src/files.rs`：授权根保护、固定忽略项、跨平台路径校验、20,000 条目限制；约一万文件的产品范围不等于删除这些安全限制。
- `Store` 使用 SQLite records bucket，适合增量增加版本化策略/待处理记录，无需替换存储层。
- `core/tests/sync.rs` 已有双端 Fixture、双向/撤销/过期预览/目录替换/并发/额度测试；`many_small_files` 为忽略运行的 10,001 文件样本。前端未声明测试脚本；CI 配置有 Rust 测试和 macOS/Windows 打包，但本次未重跑。

技能：codebase-onboarding、frontend-design-direction、improve-ui、blueprint。UI 判断目前来自源码和用户反馈，不声称已完成渲染审计。公开对标只查阅 [Syncthing 文件夹模式](https://docs.syncthing.net/users/foldertypes.html) 和 [同步机制](https://docs.syncthing.net/users/syncing.html)，没有上传项目信息。重点借鉴“方向模式”和“强制覆盖/撤销本地变化”必须分开解释，不复制其复杂集群模型。

## 三、产品规则：四个独立维度
### 3.1 配对与任务
配对回答“信任哪台设备”；目录授权回答“允许访问哪些目录”；任务回答“两个目录怎样保持关系”。新建流程为：选设备/配对 → 双端分别授权 → 选择目录 → 方向与触发 → 预览规则与影响 → 启用。
- 将现有本机授权能力带进新建任务流程；对端未授权时显示“等待对端选择文件夹”，可在对端显示上下文请求，但选择仍由对端用户完成。
- 保留动态码与等待端确认，不改动已跑通的配对密码学。
- 接收方必须接受首次共享策略；对端不得自行把共享关系改为“个人互信”。
- 同一对目录重复创建应进入现有任务，不用 `Rpc::Link` 静默覆盖已存在的策略。

### 3.2 方向与删除语义
| 模式 | 规则 | 接收端独有文件 / 接收端修改 |
|---|---|---|
| 双向 A↔B | 沿用共同基线识别单边变化；两端同时改为冲突 | 删除可传播，但遵守删除策略与熔断；双方改动不得按时间戳盲目取胜 |
| 单向更新 A→B | A 是同路径文件的权威来源，仅向 B 新增/更新；不向 A 写入 | B 独有文件保留；B 同路径本地修改显示偏离，由人工或已批准的 A 优先规则覆盖 |
| 单向镜像 A→B | 以 A 为准，使 B 的受管目录与 A 一致 | B 独有文件进入删除计划；B 修改可被 A 覆盖，启用时明确展示并确认 |

- UI 使用真实设备名和路径，显示“MacBook → Windows · 单向更新”，不只写主/从或上传/下载。
- 单向任务允许接收端发起“获取源端更新”，但传输仍只能 A→B；共享接收者不能反向写入或修改策略。个人设备两端可管理策略，改方向必须明确确认并使旧预览失效。
- 单向镜像中的权威覆盖不是误报为双向冲突；应标识“将替换接收端本地修改”。用户选择显式模式/规则后才能自动执行。
- 排除路径不参与镜像清理，不能因为被排除而被当作“源端不存在”。
- 路径重命名暂按新增+删除展示，不承诺智能识别；目录父子依赖由后端组成操作组，避免用户只选文件却漏掉必需父目录。

### 3.3 冲突与待处理
对普通文件冲突提供：比较两端 → 使用 A 版本 / 使用 B 版本 / 稍后处理。单向模式不允许选择违反方向的覆盖。
- 文本提供受大小/编码限制的只读行差异；二进制提供设备名、大小、内容指纹、存在/缺失状态。未知格式/超限明确回退元信息，不执行 HTML、脚本或外部预览程序，不承诺解析 Office 内部内容。
- 新增有界、授权校验的预览读取 RPC；请求绑定 task/grant/path 与预览指纹，禁止利用预览接口越过授权目录。读取中内容变化则提示重新检查。
- 删除与修改冲突将“保留修改版”和“采用删除”分开展示；采用删除进入同一备份与熔断检查。结构/名称不兼容给出人工改名/移动后重新扫描路径，不提供危险强制覆盖。
- 批量操作明示当前筛选范围、受影响数量和覆盖方向；不默认选择冲突，不把不同冲突类型一键混为“最新优先”。
- “稍后处理”：保留待处理项，正常文件可继续同步，不反复弹窗。
- “忽略当前版本”：按两端稳定设备 ID + 路径 + 两端指纹/缺失状态 + 策略版本记录；任一端变化重新出现，可撤销忽略。
- “永久排除”：任务级明确相对路径/目录规则，可查看和取消；同时影响扫描、自动化和镜像删除。第一版不引入复杂脚本规则语言。
- 自动任务默认遇到真正冲突保留待处理；用户可为任务明确选择固定设备优先，执行仍受方向和权限约束。不将“处理过一次”自动升级为长期规则。
- 恢复预览中的“后续变化”仍受已有撤销保护，不能用普通冲突覆盖逻辑强行抹掉后续编辑。

### 3.4 自动同步与安全边界
自动执行运行在 Rust 后台，不能依赖 React 页面、1.1 秒 snapshot 轮询或窗口是否显示。
- 每任务 Manual / OnChange；配对/创建任务后可启用，默认不替用户勾选；首次启用自动先预览并确认初始影响。
- 本机事件去抖/等待短暂稳定，对端 dirty/重连/应用重启触发复查；推荐起始静默窗口 2 秒，作为可测试实现参数，不宣称文件已由编辑软件安全保存。
- 增加保守周期复查兜底，防 watcher 丢事件；沿用内容指纹与写前再校验。退出应用、设备离线或休眠时不会同步，不能暗示为系统级永久服务。
- 为每个任务确定唯一自动协调端；双方按同一任务/设备规则推导并认可。沿用设备级单活动批次和 coordinator，排队公平执行，避免双端自动抢跑和多任务写入重叠目录。
- 手动任务始终不被后台自动写入。手动预览中的自动任务通过后端协商的审阅保留状态暂缓自动，不依赖页面布尔值；保留状态有续约/释放/超时规则，失联或过期后旧预览不得执行，恢复自动前重扫。
- 任务暂停/暂停全部是任一端都能施加的本机安全否决：入站 Begin 与逐项写入边界也要检查，任务所有者不能远程解除对端本机暂停。已进行的单项安全完成后停止后续操作，进入已有核对路径；不能只停本机 scheduler 而让对端继续写。手动执行需显式解除对应暂停。
- 自动任务撤销前先建立两端认可、可持久化的自动暂停；无法确认则不执行撤销。撤销后显示“已恢复，自动同步暂停”，用户重新预览并明确恢复后才可自动运行，重启不得解除，避免恢复的文件立即又被镜像删除/覆盖。
- 重启后先检查 pending 批次；断线优先 reconcile，再重新扫描，不能直接重放旧计划或假称字节级断点续传。
- 自身写入触发通知后复查但不生成空历史，不进入事件死循环；新变化的 epoch 不得被旧批次清掉。
- 异常仅有限退避重试；权限拒绝、版本不匹配、根目录不可用、备份失败、内容持续变化进入可解释状态，不热循环。
- 删除风险检查是手动/自动共用的执行门槛，必须先于开放镜像删除。建议阈值：普通文件删除 ≥100，或删除 ≥10 且占目标端可比较普通文件 ≥20%；源端从非空突然变空单独阻断。阈值是推荐默认，不是绝对安全保证。
- 风险评估在拆分执行/依赖组之前进行，并叠加每任务滚动时间窗累计（建议 10 分钟）；窗口起点比较基数与删除计数持久化，成功一小批或重启不能清零。用连续每批 9 个文件的情形验证，防止分批绕过阈值。
- 根目录身份/访问异常、扫描不完整、磁盘/备份不足一律阻止相关写入，不能当作空目录。单向镜像首次大清理也须明确批准，不借“刚启用”绕过保护。
- 熔断形成独立待批准操作；一次批准绑定具体删除清单、内容指纹和策略版本，清单新增/变化必须重新批准，不永久关闭保护。正常非风险项可继续，但依赖组必须完整。

## 四、界面方案
### 4.1 信息架构与层级
左侧紧凑侧栏：任务列表（名称、状态标识）、新建任务；底部设备、历史、设置。右侧当前任务详情。保留系统字体、浅深色和现有主题 token 体系，减少无意义边框、嵌套面板和抢眼数字。
- 任务头：名称、双端路径/明确箭头、方向、手动/自动状态；主要按钮随状态变化。
- 正常态：最近核验时间与简明结果，主要动作“检查变化”或“立即同步”；不重复在标题栏和内容区放同等级入口。
- 差异态：新增/更新/删除/待决定清单，支持搜索筛选、按目录组织、展开决策；不以“内容一致率”大数字占据主视觉。
- 自动运行态：当前阶段、已处理文件/总数与字节进展、暂停；显示“还剩待决定项”，不能仅显示全绿成功。
- 稳定操作区：列表底部与任务详情对齐的操作栏，显示明确的选择影响和执行动作，不使用游离且遮挡信息的浮动按钮岛。
- 配对入口主要位于设备/新建流程，不长期占据每个任务详情标题的黄金区域。
- 帮助可折叠，但权限说明、覆盖/删除后果、错误恢复建议不使用默认隐藏的 `Hint` 承载。
- 基础任务管理：重命名、查看策略、暂停/恢复、移除关联；移除任务不删除真实目录内容，撤销目录授权是单独操作。

### 4.2 状态契约
| 状态 | 必须展示 | 下一安全动作 |
|---|---|---|
| 未连接/空状态 | 当前缺的是设备、授权还是目录关系 | 连接设备 / 选择文件夹 |
| 等待对端授权 | 哪台设备待操作，不是假加载 | 对端选择后重试 / 取消 |
| 离线 | 最后已知状态不是当前核验结果 | 等待重连 / 检查连接 |
| 扫描 | 当前阶段，不编造百分比 | 取消扫描（实现支持后）/ 等待 |
| 有变化 | 实际动作、方向、删除与覆盖数量 | 审阅 / 按已批准规则执行 |
| 冲突/熔断 | 原因、影响与未解决数量 | 比较 / 决策 / 稍后处理 |
| 同步中 | 阶段、文件/字节进展 | 停止后续操作，并说明不撤销已完成部分 |
| 部分完成/中断 | 已完成与未完成的区别、是否需双端核对 | 重连核对 / 重新预览 |
| 完成 | 是所选操作完成还是所有受管文件一致 | 查看历史 / 安全撤销 |
| 权限/空间失败 | 具体失败点与本机/对端归属 | 修复权限/空间后重试 |

原型和最终验收覆盖 1120×780、680×560 及较宽桌面窗口，浅/深色、长中英文设备名/路径、键盘与焦点。侧栏在窄窗可收起但状态可见，macOS 不遮挡交通灯/拖动区，Windows 保留自然窗口操作。不以网页手机断点代替桌面最小尺寸测试。

## 五、实现架构与兼容
### 5.1 权威策略模型
在 Task/关联策略中引入版本化 TaskPolicy：稳定的两端 device/grant ID、方向及 source_device_id、触发、信任类型/策略所有者、冲突/删除/排除规则、policy_revision。不要持久化“本机优先”或局部 target=0 作为跨端主机身份。
- `mirror` 只转换展示/操作视角；策略设备 ID/所有者不翻转。
- 个人互管意味着已授权管理任务，不等于可扩大对端目录授权；共享接收者可拉取、查看与提出待处理请求，不能改策略或反写。
- 策略更新用 expected revision / 摘要进行双方握手；冲突或中途掉线标记待核对、禁止自动执行，不使用最终写入覆盖对方。
- 新建/更新 Link、Begin、预览读取、冲突决策、排除规则修改都校验授权；关键方向/所有者限制落在接收端与 Engine 写前校验，不靠 UI 隐藏。
- 一个可写目录不允许参加多条可能互相写入的自动任务；检测重叠根/成环关系并给出可解释限制。此版本不承诺多条一对一任务等价于多端一致性集群。

### 5.2 显式决策到既有执行链
保留 `compare` 作为事实比较基础，增加策略驱动规划层（建议 `core/src/policy.rs`）和冲突决策层（建议 `core/src/conflicts.rs`）。
流程：`inspect` 生成双端事实和冲突 → 受权决策解析为具体操作 → 后端返回新的可执行 Plan/digest → `execute` → 现有备份/传输/校验/历史/撤销链。
- 决策绑定原 Plan、路径、稳定设备 ID 和两端期望内容；前端不得提交任意 before/after 冒充批准结果。
- Plan 摘要包含有效策略版本、相关忽略决策及解析后的操作；策略/内容变化使旧预览失效。
- 当前 `selected: Vec<String>` 不足以表达新决策；命令契约扩展为明确选择/决策标识，并由后端校验。依赖组由后端展开，确认页计数必须对应最终实际操作。
- 失败、跳过、当前版本忽略不写成已同步的共同基线；只有已验证应用的操作和两端真实相同项可推进基线。
- 备份及 Work 记录保留实际目标、前后指纹和策略快照/引用，撤销同样遵守当前授权/方向；旧双向批次不能借撤销写入现在只读的主机。不能安全撤销时说明原因，不静默放宽权限。

### 5.3 后台与可观测状态
新增 `core/src/scheduler.rs` 组织 dirty→稳定→扫描→规划→执行/待决定→完成/暂停；复用 Node 会话、coordinator、Engine batch，而非另写同步器。Snapshot 扩展为结构化每任务状态及进度，React 负责展示，不用字符串推断是否成功。状态至少包括离线、空闲、排队、扫描、同步、待决定、熔断、暂停、待核对和失败。

### 5.4 存储与协议迁移
- records 增加显式 schema/策略版本与迁移记录；迁移前保护本机状态，失败可停止升级而不覆盖原始数据库。
- 旧任务迁移保持“手动+双向”，不自动开启后台写入。旧关系需明确归类个人/共享后才能启用新自动/权限特性，不能默认提升为个人互信。
- 保持旧历史可读；兼容旧 Work/恢复记录，不通过宽松反序列化默认值赋予新权限。存在未完成旧批次时优先处理兼容恢复；不支持安全恢复则阻止开始新批次并说明所需版本。
- 当前协议有统一版本检查；修改策略/决策契约时升级协议，两端能力不匹配明确提示升级，不静默降级到无方向约束的旧执行。

## 六、便携与一键交接
### 配置迁移
使用版本化 JSON（建议 `core/src/portability.rs`）：导出任务模板、显示名称、策略意图、排除规则和可迁移偏好；不导出私钥、凭据、信任授权、动态码、历史/备份或正在执行的批次。路径仅作重映射提示。
导入时限制大小、验证字段/路径规则、展示差异；重新匹配设备并配对、重新选择路径/授权，导入任务初始禁用自动执行，用户预览后启用。凭据继续留在系统 keyring。

分发推荐沿用 macOS .app（可 ZIP 分发）与 Windows 完整离线安装包，同时验证已具备 WebView2 的 Windows 设备能否使用轻量免安装包。当前 `tauri.conf.json` 配置 offlineInstaller，离线依赖会增加包体；“零账号、零外部服务”不等于 Tauri 没有系统 WebView 依赖。依照 [Tauri Windows 分发说明](https://v2.tauri.app/distribute/windows-installer/) 保留可离线安装的后备方案，不为缩包直接 skip 运行时检查。macOS 的签名/公证及 Windows 的安全提示明确说明，不承诺绕过系统检查或未经验证的零安装。

备份边界也必须在产品中准确说明：SyncFu 保存的是自己执行覆盖/删除前的旧内容，不是持续记录用户所有本地编辑的整机备份服务；仅有同步副本不等于独立灾备。

### 离开前一键交接
选“我要切换到哪台设备”与相关任务 → 复查变化 → 按各任务已批准规则执行（手动任务仍审阅）→ 集中处理例外 → 给出截止本次复查的交接结果。
离线、源文件继续修改、冲突未解决、方向不允许、部分完成都必须列出，不能宣称“已带齐”。使用已有任务/调度/核验链，不绕过权限、不修改模式、不阻止用户离开，也不承诺持续编辑下的原子快照。原型展示入口，后续在可靠闭环基础上实现。

## 七、分阶段施工与验收出口
以下为顺序依赖；共享契约、Node/Engine 和 UI 状态均有交叉，不为追求并行拆成互相矛盾的独立改造。**P1—P3 合起来构成首个正式可用升级，P2 只是内部可验证里程碑，不把“只有手动的新界面”当作满足手动/自动同等重要的最终交付。** P4 仍属已确认的完整路线。

实施前先保留可恢复的源码快照与当前状态样本（排除凭据/真实私有内容），弥补当前无 Git 的回退条件。每阶段保持可运行，失败时先停用新增自动路径；已有实际写入只能走受保护撤销，不能以回退代码冒充恢复数据。

### P0 — 交互原型与规则定稿（批准后的第一交付）
- 在不访问真实目录/不写文件的预览模式构建侧栏、任务详情、新建流程、方向/自动设置、冲突比较/决策、熔断和交接示例。
- 复用 `src/preview.ts`，明确标注示例数据及不可执行；不把假成功接到真实命令。
- 先形成状态/布局契约，再制作可运行原型与截图；验证用户能看懂源/目标、更新/镜像、手动/自动与三种忽略。
- 修改代表文件：`src/App.tsx`、`WindowToolbar.tsx`、`DiffView.tsx`、`PairDialog.tsx`、`components.tsx`、`styles.css`、`preview.ts`；按责任拆出 TaskSidebar/TaskDetails/TaskWizard，不重建重复组件库。
- 出口：用户体验并确认原型；已有真实桌面命令路径不被示例模式破坏。原型可以使用独立入口避免影响正式页面。

### P1 — 策略、权限与迁移契约（依赖 P0）
- 实现 TaskPolicy、稳定 ID/版本、方向规划、双方策略协商、个人/共享授权和协议迁移；保留现有恢复链。
- 在开放破坏性模式之前实现共用删除风险评估、累计窗口、一次批准绑定和执行端校验，以及入站安全暂停准入；P3 仅复用并接入自动调度，不能到 P3 才补安全门槛。
- 关键文件：`core/src/model.rs`、`policy.rs`、`node.rs`、`engine.rs`、`store.rs`、`lib.rs`；`src-tauri/src/main.rs`、`src/types.ts` 同步契约。
- 先加政策矩阵、权限拒绝、风险/暂停、旧数据迁移与旧计划失效测试，再接执行。
- 出口：三种方向在双端视角一致；反向写入/接收端改策略/旧 Link 覆盖均被后端拒绝，旧任务不自动开始写入，缺少风险批准的破坏性计划不能执行。

### P2 — 手动同步与冲突完整闭环（依赖 P1）
- 实现冲突解析、文本/元信息预览、批量决策、三种不处理语义、父子依赖组；接入新 UI 与备份/历史/撤销。
- 关键文件：`conflicts.rs`、`model.rs`、`node.rs`、`engine.rs`、`files.rs`；`src/DiffView.tsx`、`src/App.tsx` 与新 ConflictReview 组件、`src/api.ts`/types。
- 出口：新建任务→检查→选择方向/冲突→最终影响确认→备份执行→结果与安全撤销可在真双机跑通；跳过项仍在待处理，不谎报所有文件一致。必须验证大规模删除、源骤空、批准后清单变化重新阻断，不能仅测常规成功路径。

### P3 — 自动同步与熔断（依赖 P2）
- 实现 OnChange 调度、去抖、重连/重启复查、watcher 兜底、单协调端、串行队列、暂停/恢复、熔断与异常恢复。
- 关键文件：`scheduler.rs`、`node.rs`、`engine.rs`、`src-tauri/src/main.rs`；UI 按结构化状态展示。
- 出口：关闭窗口后自动同步继续；普通变化无需逐次确认；冲突/大量删除/源异常安全暂停；双方同时变化无重复批次/活锁。

### P4 — 配置迁移、交接与发行收尾（依赖 P3）
- 配置导出导入、新环境重新授权、一键交接；优化首次引导、任务管理、托盘状态/入口和轻量分发说明。
- 关键文件：`portability.rs`、`store.rs`、`node.rs`、`src-tauri/src/main.rs`、`src-tauri/tauri*.conf.json`、设置/交接 UI、`README.md`、`.github/workflows/ci.yml`。
- 出口：导出不含密钥，导入不自动写入；交接不假报成功；macOS/Windows 分发实测，体积/启动等先测量再承诺改善数值。

## 八、验证计划
### 自动化与回归
- 沿用现有双端 Fixture 与 `cargo test --locked -p syncfu-core`；`cargo fmt --all --check`、`npm run build`，桌面 `cargo check --locked -p syncfu`。
- 模式矩阵：双向、A→B/B→A 更新/镜像 × 手动/自动 × 个人/共享；从任一端 inspect/execute 的结果与权限一致。
- 文件情形：首次不同内容、单端修改、双方修改、删改冲突、目标独有、目录父子依赖、非法名称/链接、排除子目录在镜像中不被删。
- 决策情形：A/B 覆盖、稍后、版本忽略再编辑、永久排除撤销、批量筛选范围、普通冲突与撤销后续编辑隔离。
- 安全情形：预览后编辑/改策略/撤授权、共享端伪造 Link/Begin/预览读取、从机尝试反写、旧协议、两端策略不一致、空间不足与备份失败。
- 调度情形：事件突发、自身写入、事件遗漏兜底、远端变化、重启、手动审阅与自动竞争、两端同时运行、多个任务排队、断线/reconcile、熔断阈值边界与源根不可用；另测接收端暂停阻止远端 Begin/后续 Apply、审阅保留过期、连续多批各删 9 个/重启后继续累计、一次风险批准不能覆盖新增删除。
- 自动撤销专项：镜像删除撤销、覆盖撤销后维持两端自动暂停，重启也不重做原操作；人工重新预览恢复自动后才可重新规划。调度测试使用可控时钟，不靠长 sleep 证明正确。
- 持久化：旧任务/历史/未完成 Work 的迁移夹具；pending/忽略/暂停重启恢复；配置导入失败不改变现有任务。
- 前端在批准实施后补最小 Vitest + React Testing Library 测试基础，覆盖决策状态、模式/权限禁用、示例与真实命令隔离；不在调研阶段安装依赖。

### 界面与真实双机
- 按 frontend-design-direction 建立本地证据记录，覆盖空、加载、错误、部分完成、成功、权限及其恢复入口；使用项目启动方式与 Browser 工具核验原型、尺寸、长文本、浅深色、键盘/焦点和减少动画。
- 实施时才启动/截图，截图与报告保存在项目可访问目录；不上传至外部设计服务，不把源码审阅当作渲染验收。
- 用 `many_small_files` 原有忽略样本测首次/无变化/1%变化扫描和传输；记录硬件/文件样本，避免凭感觉承诺提速或悄悄移除安全限制。
- 必须独立记录 macOS↔Windows 真双机：配对、授权、三种方向、自动变化、共享权限、冲突覆盖、删除熔断、断线核对、重启和撤销。回环测试/浏览器示例不能替代这一步。
- 任何本机无法验证的平台/设备明确标为待用户或 CI 验证，不报告已完成；当前用户既有双机跑通是背景，不是本次复测证据。

## 九、计划变更原则
新需求记录为明确变更，不把未选择的创意自动塞入交付。阶段内发现不能安全支持的情形先提供原因和安全路径，不静默退化为“最新时间覆盖”或删除保护失效。每阶段出口先验收再进入后续依赖；若接口需调整，同步修改 Rust/桌面命令/TS 契约和相应测试。当前不授权提交、推送、发布、安装依赖或在用户真实数据上试验。
